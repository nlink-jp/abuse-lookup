# abuse-lookup — アーキテクチャ

本書は abuse-lookup が*なぜ*この設計なのかを説明します。*何を*するかは
[README](../../README.ja.md)、貢献者向けの地図は [AGENTS.md](../../AGENTS.md) を
参照してください。

## 中心的な緊張: オンライン API と、オフライン的な使い心地

abuse-lookup は `asn-lookup` の姉妹品ですが、両者はアーキテクチャ上は正反対です。
asn-lookup はバルク DB を一度落とせば以降オフラインで答えます。AbuseIPDB には
少数 IP 調査に適したバルクダウンロードが無く、**ライブ照会は毎回、レート制限のある
API へのネットワーク呼び出し**です（無料枠 1,000 checks/日）。

共通の目的 —「AI ツールが過剰な API コールなしに IP を調査できる」— は、ここでは
バルク DB ではなく **ローカル TTL キャッシュ**で達成します。調査中は同じ IP を何度も
引きがちで、12 時間キャッシュはその反復をゼロコストの読み取りに変えます。この一つの
判断が設計全体を規定します。

## 一つのエンジン、二つのフロントエンド

`internal/engine` が照会フロー全体（IP 検証 → キャッシュ参照 → ミス時 API 呼び出し
→ キャッシュ書き込み）を保持します。CLI（`internal/app`）と MCP サーバー
（`internal/mcp`）はその薄いシェルです。実装が一つしかないため、キャッシュ挙動・
IP 検証・エラー処理が乖離しません。

## ネットワーク無しでテスト可能

API クライアントは具象型ではなく interface（`abuseipdb.Client`）です。よってエンジンと
両フロントエンドはモックでテストでき、ライブキー不要・フレーク無し・クォータ消費なし。
本番の `HTTPClient` は `/check` と `/reports` を一つの `do()` に集約し、429 処理・
レート制限ヘッダ解析・エラー整形を一度書いて共有します。

## 嘘をつかないキャッシュ

キャッシュで問題になる故障は 2 つ、鮮度と破損です。

- **鮮度**はファイル mtime ではなくレコード内のタイムスタンプ（`FetchedAt`）で判定
  します。mtime はコピーやバックアップで書き換わりますが、レコード内タイムスタンプは
  ファイルがどう移動しても真実です。
- **破損**は各エントリを `os.Root` 経由でアトミック（temp + rename）に書くことで
  回避します。読み手は「以前の完全なファイル」か「新しい完全なファイル」のどちらかだけを
  見て、書きかけを掴みません。壊れたファイルはエラーではなくキャッシュミス扱いです。

キャッシュキーは `(IP, max-age, verbose)` の組です。これらは API レスポンスを変える
ため、一つのキーに潰すと誤ったデータを返します。通報（reports）は意図的にキャッシュ
しません — ページネーションされた詳細取得であり、ページ送りは呼び出し側が制御します。

## 大きい通報ページのファイル媒介

一つの IP に数百件の通報があり得ます。フルページをインライン返却すると MCP クライアントの
context を圧迫するため、`get_reports` はページメタ情報と小さなプレビューを返し、
フルページはファイルに書き出してパスのみ返します（`truncated: true`）。これは
asn-lookup の `lookup_asn` や voice-studio-mcp と同じパターンです。

出力先は**呼び出し側が用意**します（`workspace_root`）。サンドボックスではサーバーが
`$HOME` 配下に書けないことが多いため、呼び出し側が自分のファイルツールで書き込み可能な
ディレクトリを用意します。書き込みは `os.Root` でそのディレクトリに封じ込められ、
agent が書ける workspace に仕込まれた symlink でも外へ書き出せません。ファイル名は
サーバー生成なので、呼び出し側が leaf 名を制御することはありません。

## 秘密情報の扱い

API キーは全リクエストを認証しますが、終始秘密として扱います: 送信は `Key` ヘッダのみ
（クエリパラメータには入れない）、ログにもエラーにも出しません。コマンドラインフラグ
にも意図的にしていません — フラグ値はシェル履歴やプロセス一覧に残るためで、キーは
環境変数か config ファイルからのみ受け取ります。

## スコープ: read-only

AbuseIPDB には共有・公開 DB へ投稿する書き込み系エンドポイント（`report` /
`bulk-report` / `clear-address`）もありますが、これらは外向きの副作用でありスコープ外
です。abuse-lookup は評判を*読む*だけです。これにより、グローバルデータセットへの
意図しない投稿リスクなく、MCP 経由で AI に安全に公開できます。
